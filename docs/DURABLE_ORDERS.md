# 발송 전 저장과 재시작 후 주문 대사

`FundedJournal`은 [현금·수량 예약 계층](ORDER_FUNDING.md)의 명령과 결과를 SQLite에 저장합니다.
동결된 IOC 완료 이벤트를 저장하는 기존 [ExecutionJournal](JOURNAL.md)과 별도 스키마입니다.
입력·가상 거래소·체결은 모두 `SYNTHETIC_TEST_ONLY`이며 실제 통신은 하지 않습니다.

```bash
python examples/durable_order_recovery.py
python examples/durable_order_recovery.py --crash
python -m pytest tests/test_funded_journal.py tests/test_durable_order_case.py -q
```

## 한 명령의 경계

```mermaid
flowchart LR
    A["명령 ID·요청"] --> B["BEGIN IMMEDIATE"]
    B --> C["기록 재생·요청 검증"]
    C --> D["명령·결과·주문/계정 스냅샷 저장"]
    D --> E["COMMIT"]
    E --> F["새 명령일 때만 outgoing 반환"]
    F --> G["호출자가 가상 거래소에 전달"]
```

`submit(command_id, order, now_ns=..., marks=...)`는 승인·예약을 커밋한 뒤 발송할 `outgoing`을 반환합니다.
승인 거부도 사유와 함께 저장하되 발송 명령은 없습니다.
`request_cancel(command_id, client_order_id)`도 취소 요청 상태를 먼저 저장합니다.
유효 응답을 반영하는 `apply()`는 체결·현금·보유 수량·잔량 예약을 함께 저장합니다.
저장 실패 시 호출자는 발송할 결과를 받지 못합니다.

`command_id`는 로컬 저널 명령 ID이며, 거래소 주문의 `client_order_id`와 구분합니다.
같은 명령 ID·동일 요청을 다시 호출하면 `status="duplicate"`, 기존 결과와 순번,
**`outgoing=None`**을 반환합니다. 요청이 다르면 거부합니다.
저장된 `result.order`는 감사용 과거 명세입니다. 이것을 새 발송 대상으로 사용하지 않습니다.
발송에는 처음 성공한 호출의 `outgoing`만 사용해야 합니다.
다른 로컬 명령 ID로 같은 승인 주문을 제출해도 생명주기 계층에서 거부합니다.

각 작업은 최신 DB 기록을 읽습니다. 다른 핸들의 커밋을 무시하는 메모리 캐시는 없습니다.
쓰기 트랜잭션은 SQLite로 직렬화하며, 동시에 두 주문이 같은 현금을 중복 예약할 수 없는지 테스트합니다.
각 SQLite 연결은 생성 스레드에서 사용합니다. 메모리 manager와 가상 거래소도 생성 스레드 전용입니다.
다른 스레드의 콜백은 소유 스레드로 전달하며, 별도 SQLite 연결 간 쓰기는 트랜잭션으로 직렬화합니다.
연결은 `synchronous=FULL`, busy timeout5초를 설정합니다. 특정 하드웨어의 전원 손실까지 시험한 것은 아닙니다.

## 재시작 시 무엇을 알 수 있는가

`recover()`는 검증한 계정/주문 스냅샷, 커밋 명령 수, 모든 미종료 주문의 `reconciliation` 목록을 반환합니다.
`pending_new`도 조회 대상입니다. 이 상태만으로 요청이 아직 발송되지 않았다고 판단할 수 없습니다.
정상 보유 중인 open/partial 주문도 누락 체결이 있을 수 있으므로 목록에 포함합니다.
라이브 연결·조회 스케줄러는 없으며 호출자가 목록의 client ID로 가상 거래소에 조회합니다.

`reconcile(command_id, client_order_id, report)`는 조회 결과를 저장합니다.

| 조회 결과 | 처리 |
|---|---|
| 결과 없음(`None`) | 미접수 확정으로 해석하지 않음. 신규/취소 미응답을 unknown으로 표시하고 예약 유지 |
| 누적 부분 체결 | 유실된 접수/체결 응답을 누적 상태로 복원하고 잔량 예약 유지 |
| 아직 열린 주문, 취소 unknown | 주문 상태를 확인해도 지연된 취소의 미해결 상태는 유지 |
| 누적 체결을 포함한 취소 확정 | 체결 대금 반영 후 미체결 예약 해제 |
| 전량 체결 | 예약을 체결 사실로 대체. 취소가 대기 중이면 too_late |
| 다른 주문의 조회 응답·상충하는 보고 | 트랜잭션 전체 거부, 계정과 명령 기록 보존 |

자동 재전송은 없습니다. **커밋 직후 실제로 발송되지 못한 주문도 예약이 계속 남을 수 있습니다.**
조회 부재만으로 지연 전송 가능성을 제거할 수 없기 때문입니다.
이 단계는 안전하게 멈추는 쪽을 택하며, 세션 fencing이나 거래소별 재시도 보장으로 해당 상태를
최종 해소하는 절차는 구현하지 않았습니다. 네트워크의 exactly-once delivery 보장이 아닙니다.

## 공개 복구 사례

초기 현금1,000에서 A buy10@limit100을 저장하고 접수 여부를 모르는 상태로 재시작합니다.

1. 같은 명령을 확인해도 발송 명령이 나오지 않습니다. 예약1,000을 복원합니다.
2. 조회가 비어 있어도 예약은 유지하며 상태를 unknown으로 저장합니다.
3. **원래의 지연 요청**이 뒤늦게 도착해 A3@99에 체결됩니다. 조회로 현금703/예약700을 복원합니다.
4. 취소 요청을 저장한 뒤 다시 종료합니다. 그사이 A2@100이 추가 체결되고 거래소에서 취소됩니다.
5. 재시작 후 누적 조회로 현금503/예약0/A5를 복원합니다. 뒤늦은 ACK·두 체결 보고는 대금을 다시 반영하지 않습니다.
6. DB를 재열어 같은 최종 스냅샷과 조회 대상0개를 확인합니다.

현금은 `1000 - 3×99 - 2×100 = 503`입니다. 수수료0의 수동 합성 회계 사례입니다.
기본 예제는 임시 DB를 만들고 정리하며 재열기를 보여줍니다.
`--crash`는 부모 프로세스에 가상 거래소를 유지하고 자식 클라이언트만 SIGKILL로 종료합니다.
취소 요청이 커밋된 뒤 추가 체결·취소 응답을 전달하지 않은 상태에서 종료하고, 재시작 후 누적 조회로 복원합니다.
동일 명령과 동일 보고의 중복 전달 뒤에도 주문·계정 스냅샷이 같아야 성공합니다.
거래소가 생성한 체결에서 독립적인 Decimal 산술로 현금·수량을 계산하고 DB의 체결 ID/사실과 비교합니다.
이 검산은 OMS의 account/replay 함수를 재사용하지 않습니다. 잘못된 잔고를 주면 실패하는 테스트도 있습니다.
이 강제 종료 데모는 POSIX 파이프와 SIGKILL을 사용하는 macOS/Linux용이며 실제 거래소 계좌 조회는 아닙니다.

## 검증과 현재 한계

[강제 종료·저장 테스트](../tests/test_funded_journal.py)는 별도 Python 프로세스에서 `os._exit()`를 사용합니다.
신규 승인, 부분 체결, 취소 확정 각각에서 명령 삽입 후/스냅샷 기록 후/커밋 직후 종료를 확인합니다.
커밋 전에는 명령과 스냅샷이 함께 롤백되고, 커밋 후에는 함께 복구돼야 합니다.
커밋 직후 종료는 호출자에게 결과가 반환되기 전의 모호한 상황도 포함합니다.
가상 거래소가 체결한 뒤 클라이언트가 보고를 저장하지 못한 상황도 프로세스 종료로 검증합니다.

재열기와 매 작업에서 순번 연속성, 명령 결과의 결정적 재생, 저장 스냅샷 일치를 검사합니다.
초기 상품·정책과 코드 파일의 SHA-256을 고정하며 정의가 바뀌면 열기를 거부합니다.
해시는 인증이 아니며 악의적인 DB 전체 재작성에 대한 변조 방지 보장은 없습니다. 자동 이관·수리는 하지 않습니다.
기존 경로는 덮어쓰지 않고, 없는 DB를 열 때 새 DB를 만들지 않습니다.

누적 명령10,000건부터 신규 submit을 중단합니다. 같은 명령 ID의 기존 결과 조회는 계속 허용합니다.
이미 승인한 주문의 apply/reconcile/request_cancel/mark_unknown과 복구는 중단선 이후에도 저장·재생합니다.
이 변경은 포화 시 유효 체결과 취소 확정까지 거부하던 문제를 해결합니다.
JSON 레코드당8MiB와 상품/주문/체결 개수 제한은 유지합니다. 정리 감사 로그의 전체 크기는 제한하지 않습니다.
디스크 부족이나 과도한 재생 비용은 여전히 실패 원인이며, 자동 로그 순환·압축·체크포인트는 구현하지 않았습니다.
매 작업의 전체 재생을 유지합니다. 이후 측정한 합성 지연과 불변 이력 복사의 효과·제한은
[현재 성능 근거](OPERATIONAL_EVIDENCE.md)에 있습니다. 실제 거래소 처리량·네트워크 지연 검증은 아닙니다.
단일 로컬 DB와 안정적인 가상 거래소 주문/체결 ID를 가정합니다.
실제 연결 복구, 다중 호스트 dispatch 소유권, 자동 재시도, 정정, 백업·마이그레이션은 범위 밖입니다.
이번 코드 변경으로 이전 코드 해시에 고정된 DB는 열기를 거부합니다. 이관 없이 새 합성 실행으로 검증합니다.
