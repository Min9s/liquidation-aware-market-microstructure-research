# 합성 주문 생명주기 — v2 첫 단계

기존 IOC 완료 이벤트 재생과 별도로, 응답이 지연·유실·중복되는 주문의 상태를 다룹니다.
단일 가상 거래소의 **직접 정의한 누적 상태 프로토콜**입니다. 실제 거래소나 FIX의 구현이 아닙니다.

```bash
python examples/order_lifecycle.py
python -m pytest tests/test_order_lifecycle.py tests/test_order_lifecycle_case.py -q
```

## 대표 사례와 손계산

모든 입력은 `SYNTHETIC_TEST_ONLY`입니다. 수량 단위1, 가격 단위1의 가상 BTC 상품을 사용합니다.
아래 순서는 프로그램이 명시적으로 정하며 실제 통신이나 시장 대기열은 없습니다.

| 단계 | 거래소/전달 상황 | 로컬에서 확인할 상태 |
|---|---|---|
| 1 | buy10, limit100 요청 후 응답 없음 | `pending_new` → `unknown`; 자동 재전송 없음 |
| 2 | 요청 도착 전 조회는 결과 없음 | `unknown` 유지; 미접수 확정으로 해석하지 않음 |
| 3 | 거래소 접수, 3개를99에 체결; 응답 유실 | 거래소 조회의 누적 상태로 `partially_filled`, 체결3 복원 |
| 4 | 취소 요청 후 2개를100에 추가 체결 | 취소 요청만으로 체결을 막았다고 가정하지 않음 |
| 5 | 취소 확정 응답이 앞선 체결 응답을 추월 | 누적 체결5, `canceled`; 미체결5, 살아 있는 잔량0 |
| 6 | 늦은 접수·체결 응답과 취소 응답 재전달 | 과거 상태로 되돌리지 않고 체결도 추가 반영하지 않음 |
| 7 | 내보낸 메모리 로그 재생 | 최종 주문 상태·체결 수·수량·현금 흐름 동일 |

순체결 수량은 `3 + 2 = 5`, 현금 흐름은 `-(3×99 + 2×100) = -497`입니다.
현금 흐름은 체결 대금의 부호 합계이며 수익, 계정 잔고, 담보 또는 파생상품 손익이 아닙니다.
수수료·펀딩·승수·평가 가격은 이 모듈의 계약에 포함하지 않습니다.

## 상태를 나누는 이유

주문 상태는 `pending_new`, `unknown`, `open`, `partially_filled`, `filled`, `canceled`, `rejected`입니다.
취소 요청의 상태는 별도로 `none`, `pending`, `unknown`, `canceled`, `too_late`를 기록합니다.
취소 요청이 미해결인 동안에도 추가 체결을 반영합니다. 전량 체결이 먼저 확정되면 주문은
`filled`, 취소는 `too_late`로 남습니다. 뒤늦은 취소 거부가 이를 되돌리지 않습니다.

`mark_unknown()`은 미응답을 호출자가 판단해 표시합니다. 타이머나 자동 재시도는 없습니다.
취소 미응답 뒤 조회한 주문이 아직 열려 있어도, 지연된 취소 요청이 남아 있을 수 있으므로
취소의 `unknown`을 해제하지 않습니다. 같은 로컬 주문 ID 재제출과 미해결 취소의 중복 요청은 거부합니다.
거래소 쪽은 동일 ID·동일 명세의 재접수를 같은 주문 조회로 처리하고 명세가 다르면 거부합니다.
이 멱등성은 이 가상 프로토콜의 규칙이며 실제 거래소의 보장을 뜻하지 않습니다.

`remaining_quantity`는 요청 수량에서 누적 체결을 뺀 미체결 수량입니다.
`last_confirmed_working_quantity`는 마지막 거래소 상태 기준 잔량으로, 종료 주문이면0입니다.
거래소 상태를 아직 모르면 `null`입니다. 미응답·취소 요청 중에는 현재 실제 잔량을 보장하지 않습니다.
`needs_reconciliation`은 명시적으로 `unknown` 처리된 주문/취소 요청을 표시합니다.

## 누적 보고 계약과 검증

보고에는 `source_kind`, `event_id`, `report_type`, `state`만 허용합니다.
`state`는 거래소 ID, 거래소 주문 ID, 양의 정수 revision, 주문 명세, 상태,
누적 체결 목록, 신규 주문 거부 사유를 포함합니다. 조회도 같은 상태 형식을 사용합니다.

- 각 주문의 revision은 접수·체결·취소가 진행될 때 증가합니다. 조회·취소 거부는 현재 revision을 보냅니다.
- 보고 한 건에 **전체 누적 체결**이 있으므로 revision이 건너뛰어도 누락 체결을 복원합니다.
  체결 증분만 보내는 거래소에는 그대로 사용할 수 없습니다.
- 같은 event ID의 동일 보고는 중복입니다. 내용이 다르면 거부합니다.
- execution ID는 한 거래소 세션 안에서 모든 주문에 걸쳐 유일하며 수량·가격·주문 결합을 바꿀 수 없습니다.
- 높은 revision은 알려진 체결을 모두 포함해야 합니다. 같은 revision의 다른 상태는 거부합니다.
  이미 지나간 revision도 관측 당시 상태의 해시를 보존하므로 다른 내용으로 재전달할 수 없습니다.
  낮은 revision은 알려진 체결의 과거 부분집합일 때만 무시하며, 상충하는 종료 사실은 거부합니다.
- 틱·수량 단위·지정가·초과 체결·상태와 체결 합계·거래소/주문 결합을 검사한 뒤 반영합니다.
  검증 실패는 주문·체결·로그를 변경하지 않습니다.
- Decimal 계산은 지역 정밀도128에서 수행합니다. 입력 숫자는 기존 실행 계약의 유한 문자열 경계를 사용합니다.
  상품100개, 주문1,000개, 주문당 체결1,000개로 제한합니다.
  MAX_EVENTS=10,000은 누적 이력 기준 신규 접수 중단선입니다. 이후에도 기존 주문의 보고·취소·조회와
  로그 재생은 허용합니다. 정리 이력은 중단선을 넘을 수 있으며 전체 로그의 하드 상한은 아닙니다.

OrderManager와 SimulatedVenue는 생성 스레드가 소유합니다. 다른 스레드의 공개 메서드 호출은
상태를 읽거나 바꾸기 전에 RuntimeError로 거부합니다. 외부 콜백은 소유 스레드로 전달해야 합니다.
로그를 내보내 다른 스레드에서 replay로 새 manager를 만드는 것은 명시적인 재구성 방식입니다.

[주문 상태 처리](../src/market_microstructure/order_lifecycle.py),

미응답 조회, 변조 보고의 반영 전 거부, 매수·매도 대금 손계산과 재생을 확인합니다.

## 기존 실행 엔진과의 경계 및 다음 단계

기존 [실행 엔진](EXECUTION.md)은 합성 선형 계약의 IOC 체결·공유 담보·수수료·위험 검사를 다룹니다.
[SQLite 저널](JOURNAL.md)은 동결 입력의 완료 이벤트를 저장합니다.
이 모듈의 대기 주문·미응답·부분 체결 상태는 그 파생계약 원장/저장 계층에 연결하지 않았습니다.
후속 [자금 예약 계층](ORDER_FUNDING.md)은 별도 현금 계정과 기존 시세·노출 한도 함수를 연결합니다.
`export_log()`/`replay()`는 메모리 내 결정적 재생이며 프로세스 강제 종료 후의 내구성 보장이 아닙니다.

이번 구현에는 실제 주문 전송, 연결/세션 재시작, 타임아웃 스케줄러, 정정, 시장가, 자동 매칭,
호가 대기열, 실시간 운영 서비스가 없습니다. 단일 실행 구간에서 거래소/체결 ID가 안정적인 것으로 가정합니다.
대기/미응답 주문의 현금·수량 예약은 후속 계층에서 정의했습니다.
후속 [SQLite 저장 계층](DURABLE_ORDERS.md)은 명령 발송 전 저장·체결 반영·재시작 후 대사를 검증합니다.
