# 대기 주문의 현금·수량 예약

`FundedOrderManager`는 [합성 주문 생명주기](ORDER_LIFECYCLE.md)를 감싸는 주문 승인 계층입니다.
생성 스레드에서만 접근하며 다른 스레드의 직접 호출은 거부합니다. 외부 응답은 소유 스레드에서 처리해야 합니다.
매수는 현금으로 전액 지급하고, 매도는 확인된 보유 수량으로만 실행하는 합성 현금 계정입니다.
차입·공매도·수수료·펀딩·입출금·기업행위는 없습니다. 초기 현금 외 초기 보유 수량은0입니다.
기존 [실행 엔진](EXECUTION.md)의 파생계약 담보·손익 원장과는 다른 회계입니다.

```bash
python examples/funded_order_lifecycle.py
python -m pytest tests/test_funded_orders.py tests/test_funded_order_case.py -q
```

## 예약과 체결 대금의 구분

매수 승인 시 **미체결 수량 × 지정가**를 현금에서 예약합니다.
체결이 오면 실제 가격의 대금만 현금에서 차감하고, 남은 수량의 예약은 유지합니다.
지정가보다 싸게 체결되면 그 차이만큼 사용 가능 현금이 증가합니다.
매도 승인 시 미체결 수량을 보유 수량에서 예약합니다. 아직 안 들어온 매도 대금은 사용할 수 없습니다.

| 로컬 상태/사건 | 잔량 예약 처리 |
|---|---|
| `pending_new`, 신규 주문 `unknown` | 거래소 접수 여부와 무관하게 유지 |
| 취소 요청 `pending` 또는 `unknown` | 취소됐다고 가정하지 않고 유지 |
| 부분 체결 | 확인된 체결 대금·보유 수량 반영, 미체결 잔량만 예약 |
| 거래소 `canceled` | 보고에 포함된 체결을 반영한 뒤 미체결 예약 해제 |
| 거래소 `rejected` | 신규 주문 예약 전체 해제 |
| 거래소 `filled` | 체결 전부 반영, 미체결 예약0 |
| 중복·과거 보고 | 생명주기 검증 결과에 따라 중복 대금·예약 변경 없음 |

확인 전 매수 체결은 매도 가능한 보유 수량으로 사용하지 않습니다.
동일 상품에 여러 매수·매도가 대기해도 현금과 수량을 각각 합산해 중복 사용을 막습니다.
`available_cash = cash - reserved_cash`,
`available_inventory = inventory - reserved_inventory`가 음수가 되는 신규 주문은 승인하지 않습니다.

## 위험 검사 연결 범위

[기존 위험 모듈](../src/market_microstructure/execution_risk.py)의 `quote_problem()`과
`exposure_checks()`를 재사용합니다. 파생계약의 `check_entry()`나 담보 원장을 호출하는 통합은 아닙니다.
표준 정책 키는 기존과 같은 `max_order_notional`, `max_symbol_gross`, `max_portfolio_gross`입니다.

신규 매수의 주문 금액은 요청 수량 × 지정가로 검사합니다.
상품/계정 한도에는 아래 **보유·대기 합산 노출**을 사용합니다.

```text
상품 노출 = 확인된 보유 수량 × 유효 시세
          + 각 미체결 매수 수량 × max(해당 지정가, 유효 시세)
계정 노출 = 상품 노출의 합
```

매수 대기 중 시세가 내려가도 지정가 예약 노출을 줄이지 않습니다.
시세가 올라가면 높아진 평가 노출을 검사합니다. 대기 매도는 체결 전까지 노출을 줄이지 않습니다.
따라서 두 방향의 대기 주문을 상계해 신규 매수 여력을 만들 수 없습니다.

필요한 시세가 없거나 invalid·미수신·stale·다른 session이면 신규 매수를 거부합니다.
전체 노출을 계산할 수 없어도 다른 상품의 알려진 한도 위반은 남깁니다.
정확한 age 경계와 available 시각은 기존과 같이 포함합니다.
평가 시세는 직접 제공한 가격이며 호가 체결 가격이나 거래소의 시세 검증을 뜻하지 않습니다.

보유 수량만 감소시키는 매도는 진입 금액·노출 한도와 시세 부재에서 제외합니다.
수량 예약 검사는 유지하므로 공매도나 같은 수량의 중복 매도는 허용하지 않습니다.
이미 발생한 유효 체결은 신규 주문의 승인 대상이 아니며, 현재 한도 위반이나 시세 부재를 이유로 버리지 않습니다.
자동 취소·강제청산은 없습니다. `assess()`로 현재 한도 상태를 확인하고 호출자가 다음 행동을 결정합니다.

## 대표 사례의 독립 검산

입력은 모두 `SYNTHETIC_TEST_ONLY`, 초기 현금1,000, 수수료0, A/B 평가 시세100입니다.
체결과 응답 순서를 사람이 지정한 회계 사례이며 전략 성과가 아닙니다.

| 사건 | 현금 | 예약 현금 | 사용 가능 현금 | 확인된 보유 수량 |
|---|---:|---:|---:|---|
| A buy10@limit100, 미응답 | 1,000 | 1,000 | 0 | 없음 |
| 조회로 A3@99 복원 | 703 | 700 | 3 | A3 |
| 취소 미응답 중 거래소에 A2@100 추가 체결 | 로컬703 | 로컬700 | 로컬3 | 로컬 A3 |
| 누적 체결5를 포함한 취소 확정 | 503 | 0 | 503 | A5 |
| B buy5@limit100, 미응답 | 503 | 500 | 3 | A5 |
| A sell5@limit110 승인 | 503 | 500 | 3 | A5, 그중5 예약 |
| A2@111 매도, B5@99 매수, 매도 잔량 취소 | 230 | 0 | 230 | A3, B5, 예약 수량0 |

처음의 B 매수는 현금 부족으로 거부됐으므로 거래소 주문이 없으며, A 취소 확정 후 같은 ID로 다시 승인받습니다.
반면 승인 뒤 미응답인 주문은 같은 ID로 재제출할 수 없습니다.
A5 매도 대기 중 추가 A1 매도는 예약 수량 부족으로 거부합니다.

최종 현금은 `1000 - 3×99 - 2×100 + 2×111 - 5×99 = 230`,
확인된 원장과 합성 평가 시세 기준 equity는 `230 + 3×100 + 5×100 = 1030`입니다.
미응답 중의 실제 거래소 자산을 실시간으로 확정하는 값은 아닙니다.

## API·원자적 반영·재생

`submit(order, now_ns=..., marks=...)`는 승인 여부·사유·이전/예상 평가를 반환합니다.
승인된 경우에만 `order`가 들어 있으므로 이를 거래소에 전달합니다. 거부 시에는 `order=None`이며
생명주기와 예약을 변경하지 않습니다. 거부 결정도 시각·시세·사유와 함께 메모리 로그에 남깁니다.
결정 시각은 호출자가 제공하며 역행할 수 없습니다. 보고의 실제 체결 시각이나 벽시계를 추론하지 않습니다.

시세 레코드는 `quote_id`, `timestamp_ns`, `available_ns`, `session_id`, `valid`, `price`의 정확한 필드만 허용합니다.
잘못된 형식은 조용히 무시하지 않고 실패하며 상태/로그를 보존합니다.
허용된 숫자 입력을 검증한 뒤 계산은 지역 Decimal 정밀도128에서 수행합니다.
계산 결과는 입력보다 자릿수가 길어질 수 있으므로 외부 입력의 자릿수 제한을 다시 적용하지 않습니다.

변경은 후보 상태에서 검증한 뒤 반영합니다. `apply()`는 주문 상태와 현금·수량 예약을 함께 검증합니다.
`export_log()`에는 상품·정책·거래소 ID·승인 및 거부 결정·응답이 포함됩니다.
`replay(bundle)`은 이를 재생하고 승인 결과의 일치도 확인합니다. 로그는 인증되거나 변조 방지된 자료가 아닙니다.

정리 로그의 전체 크기는 제한하지 않으며 상태 복사 방식의 처리량·지연은 벤치마크하지 않았습니다.
FundedOrderManager 자체는 메모리 재생까지입니다. 후속 [FundedJournal](DURABLE_ORDERS.md)은
이를 감싸 발송 전 저장·예약 복구·재시작 후 미응답 조회를 제공합니다. 기존 파생계약 SQLite 스키마와는 별도입니다.
