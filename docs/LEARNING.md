## 기존 연구 코드 학습

프로젝트 이름은 Liquidation-Aware Market Microstructure Research이며 Python 패키지는
`market_microstructure`입니다. 먼저 `python examples/research_walkthrough.py`로
SYNTHETIC 전체 흐름을 확인한 뒤 아래 순서로 코드를 읽어 보세요.
연습 문제에서 제안하는 변경은 학습 과제이며, 현재 API의 기능이나 개발 예정 목록이 아닙니다.

## 1. bid_ask_spread

- 입력: 양의 유한한 bid/ask 가격. 숫자 문자열도 가능하며 bid <= ask가 필요합니다.
- 출력: `{"mid": ..., "absolute": ..., "bps": ...}`.
- 알고리즘: 숫자 변환 → 가격 순서 검사 → ask-bid → midpoint → midpoint 대비 bps.
- 시간·추가 공간: O(1).
- 읽을 코드: `src/market_microstructure/orderbook.py`의 `_number`, `_prices`, `bid_ask_spread`.

연습:

1. 99.5/100.5와 995/1005를 손으로 계산하세요. 가격 단위가 10배이면 어떤 값이 바뀌나요?
2. `mid` 대신 bid로 나눈 spread를 별도로 계산해 차이를 설명하세요.
3. `(bid + ask) / 2`로 바꾼 뒤 큰 가격 테스트를 실행하고 차이를 확인하세요. 확인 후 복구하세요.

## 2. order_book_imbalance

- 입력: 같은 단위의 최우선 매수·매도 수량, 각각 0 이상.
- 출력: [-1, 1]의 float. 총수량 0이면 `None`.
- 알고리즘: 수량 검사 → 합계와 overflow 검사 → 차이/합계. 0 분모는 나누지 않습니다.
- 시간·추가 공간: O(1).

연습:

1. (3,1), (1,3), (0,1), (0,0)을 직접 계산하고 각 의미를 말해 보세요.
2. 양쪽 수량에 같은 양수 배율을 적용하면 값이 유지되는 이유를 식으로 설명하세요.
3. 가격×수량 기준 불균형을 별도 연습 함수로 만들어 보세요.
   가격 99/101, 수량 3/1일 때 기존 0.5와 왜 다른가요?

## 3. notional_depth

- 입력: bid/ask 가격과 각 최우선 수량. 순서는 가격 두 개, 수량 두 개입니다.
- 출력: 매수·매도·합계 명목금액 딕셔너리.
- 알고리즘: 가격과 수량 검사 → 각 가격×수량 → 합산 → 비유한 결과 거부.
- 시간·추가 공간: O(1).

연습:

1. bid=99×3, ask=101×1에서 매수 주문으로 접근 가능한 표시 유동성은 어느 쪽인가요?
2. 계약 한 개가 기초자산 0.01단위를 뜻한다면 수량을 어떻게 정규화해야 하나요?
3. 양쪽 수량이 0일 때 depth=0과 OBI=None이 동시에 타당한 이유를 설명하세요.

## 4. trade_imbalance

- 입력: 필수 키가 있는 체결 행의 iterable과 키워드 인자 `decision_ns`, `window_ns`.
- 출력: `buy_notional`, `sell_notional`, `imbalance`, `trade_count`.
- 알고리즘: 인자 검사 → 모든 행의 필드·값 검사 → 발생/수신 시각 필터 →
  buy/sell 명목금액을 각각 모음 → `math.fsum` → 양쪽 합계 검사 → 차이/합계.
- 시간: 입력 n개에 대해 O(n). 추가 공간: 포함된 체결 k개에 대해 O(k).
  정렬은 필요하지 않지만, 입력 중복 제거는 호출자가 해야 합니다.
- 금액 합계 0이면 `None`. 관측된 매수·매도 금액이 같고 양수이면 0.0입니다.

연습:

1. 예제에서 D=100일 때 발생 99/수신 101인 체결을 제외하는 이유를 설명하세요.
2. 왼쪽 경계를 `<`에서 `<=`로 바꾸면 어떤 테스트가 바뀌어야 하나요? 실제 결과도 확인하세요.
3. 같은 체결을 두 번 넣으면 값이 어떻게 바뀌나요? trade ID를 이용한 중복 제거는
   계산 함수 밖에서 별도 연습으로 구현해 보세요.
4. 리스트 대신 누적 변수만 사용하면 추가 공간은 줄지만 합산 정확성에 어떤 변화가 있나요?
   0.1과 큰·작은 금액을 섞은 입력으로 비교해 보세요.
5. 구간 밖의 잘못된 행도 거부하는 현재 정책과, 포함 행만 검사하는 정책의 장단점을 설명하세요.

## 5. prepare_exposure, gravity, liquidation_imbalance

- `prepare_exposure` 입력: signed size, 반환된 청산가 또는 None, 양의 기준가격.
- 출력: 단일 포지션의 포함 여부·이유·상하 방향·명목금액·청산가·거리.
- 알고리즘: size/reference 검사 → 현재 명목금액 → 0 포지션·결측·잘못된 청산가·
  같은 가격·반대 방향 제외 → 포함되는 경우만 거리 bps 계산.
- `gravity` 입력: `(notional, distance_bps)` 쌍의 iterable과 양의 tau.
- 출력: `sum(N * exp(-d/tau))`. 시간·추가 공간은 노출 수 n에 대해 O(n).
- `liquidation_imbalance` 입력: up/down Gravity, 양의 epsilon. 출력: `(up-down)/(up+down+epsilon)`.
- 단일 포지션 준비와 LGI는 시간·추가 공간 O(1). 기준가격과 청산가는 서로 다른 정보입니다.

예제에서는 long 2개/99.9 → N=200,d=10bps, short 3개/100.25 → N=300,d=25bps입니다.
tau=10일 때 down≈73.57588823, up≈24.62549959, LGI≈-0.49846942입니다.
추가한 청산가 결측 포지션 1개의 명목금액 100은 제외 사유와 함께 남으며 0 노출로 바뀌지 않습니다.
이렇게 계산한 LGI는 포함된 부분 표본에 대한 값입니다.

연습:

1. tau를 10에서 25로 바꾸기 전에 가까운/먼 노출의 상대 가중치가 어떻게 달라질지 예상하세요.
2. 명목금액 300인 short가 200인 long보다 Gravity 기여가 작은 이유를 손으로 설명하세요.
3. 청산가 None을 임의의 가격으로 채우면 결과가 왜 관측 자료의 계산이 아니게 되나요?
4. `liquidation_imbalance(0,0)=0`과 자료 자체가 없는 경우를 구분하세요.
5. `epsilon=1`을 넣고 LGI를 계산하세요. 왜 기존 정의에서는 단순히 차이/합계만 쓰지 않나요?
6. float 거리 계산의 9.999999999999432와 10의 차이를 확인하세요. 단일 포지션 도우미는
   float를 사용하지만 역사 재생 `_exposure`는 Decimal로 가격 방향·거리 경계를 준비합니다.

## 6. select_asof

- 입력: 단일 entity의 기록 iterable, 판단 시각, 최대 나이, 기대한 데이터 종류·출처·대상.
- 각 행의 timestamp는 event/state time, ingested_at은 receive time입니다.
  timestamp_basis=received면 timestamp=ingested_at이며 독립적인 거래소 시각이 아닙니다.
- 알고리즘: 전체 행의 메타데이터 검사 → 판단 시각까지 받은 최신 행 → 동률 충돌 확인 →
  미래 발생 시각·clock inversion·불완전 표시·stale 검사 → 기록 또는 이용 불가 사유.
- 출력: status/reason/record/record_id/age_ns 딕셔너리. 부적격 record는 None입니다.
- 시간 O(n), 중복 ID 검사를 위한 추가 공간 O(n). 정렬이나 클래스가 필요하지 않습니다.
- 반환 행은 shallow copy입니다. 함수는 입력을 변경하지 않지만 중첩 payload는 공유합니다.
- complete와 출처는 입력 계약입니다. 실제 자식 행 대사·UTC 인증·과거 신호 게시 인증을
  수행하지 않습니다. payload의 금융값 유효성도 해당 계산 함수에서 별도로 검사합니다.

연습:

1. event=90, receive=101, decision=100인 기록을 제외하는 이유를 설명하세요.
2. 최신 기록이 불완전하고 이전 기록이 정상일 때, 이전 포지션을 되살리는 위험을 설명하세요.
3. event=99, receive=98, decision=100을 넣어 clock_inversion 결과를 확인하세요.
   event=101로 바꾸면 어떤 사유가 우선하나요?
4. max_age_ns=20일 때 age=20과 21의 경계를 직접 확인하세요.
5. 같은 수신 시각의 상충 기록에 사전 등록된 sequence를 추가하려면 무엇을 검증해야 할까요?
   현재 구현은 임의의 record_id 순서로 해소하지 않습니다.
6. source_kind=REAL_OBSERVED라고 쓰는 것만으로 데이터가 실제 관측이거나 적격해지지 않는
   이유를 설명하세요. 합성 입력을 실제 입력으로 재표시하는 기능으로 사용하면 안 됩니다.

## 원본 연구와 독립 구현의 구분

Liquidation Gravity에서 가져온 연구 정의는 지수 거리 감쇠, epsilon을 포함한 LGI,
청산가의 방향별 제외 원칙과 최신 수신 상태를 먼저 고르는 원칙입니다.
이 저장소의 코드·테스트·예제는 해당 원칙에 맞춰 독립적으로 구현·적응했으며
기존 저장 계층·수집기·Surface·모델을 실행 의존성으로 가져오지 않았습니다.
파일별 출처와 AI 보조 범위는 [PROVENANCE.md](../PROVENANCE.md)에 있습니다.

Phase 1에서 설명할 내용은 단일 노출 준비, 거리 감쇠 합산,
결측과 빈 관측의 구분, 시점별 기록 선택입니다. 실제 시장 예측력 검증은 별도 과제입니다.

## 7. replay_history — 로컬 역사 자료의 노출 시계열

- 입력: 계정·모든 자산의 자식 포지션·BTC context·BTC BBO 목록과 고정 정책 dict.
- 출력: 모든 판단 시점의 집계와 시계열 요약. 계정 주소·스냅샷 ID 자체는 출력하지 않습니다.
- 알고리즘: 수신 시각으로 정렬 → 시점까지 관측한 주소의 최신 헤더 → 자식 행 정합성·
  신선도 검사 → 당시 mid 기준 노출·거리 → Gravity/LGI → 제외 사유·분모 보존.
- 자식 행은 snapshot ID로 묶지만 판단 시점 이후 도착한 행을 과거 완전성에 사용하지 않습니다.
- ETH/SOL 자식 행을 제거하고 BTC만 읽으면 scoped_position_count 검사가 깨질 수 있습니다.
  조립에는 전체 자식 행, 노출 계산에는 BTC만 사용해야 합니다.
- 시간 반복에서 같은 스냅샷을 재사용하므로 평가 횟수는 고유 스냅샷 수가 아닙니다.
- Decimal은 가격 비교·거리에 사용하고, 지수 가중 합산은 기존 float Gravity 함수로 합니다.
  Phase 1의 float 단일 포지션 도우미와 경계 산술의 정밀도가 다르다는 점을 확인하세요.

연습:

1. 합성 예제에서 BTC long의 청산가를 None으로 바꾸고 알려진 노출과 포함 노출을 비교하세요.
2. 미래 주소를 추가해도 그 주소가 처음 수신되기 전의 known_accounts와 Gravity가 같은지 확인하세요.
3. 최신 계정 헤더의 자식 하나를 제거했을 때 이전 정상 포지션으로 돌아가면 왜 위험한가요?
4. context 중간 행을 제거하고 미계산 시점이 null과 이유를 남기는지 확인하세요.
5. 같은 스냅샷의 나이가 허용 한도를 넘을 때, 과거 유효/이후 제외 수가 왜 겹치는지 설명하세요.

## 8. historical_io — 계산과 저장을 분리하기

- Parquet 파일만 읽는 선택 모듈이며 PyArrow가 필요합니다. 계산 코어에는 영향을 주지 않습니다.
- pin 단계는 입력 파일·정책과 manifest SHA를 고정합니다. 실제 자료를 복사하지 않습니다.
- replay 단계는 같은 고정 파일의 읽기 전후 SHA를 확인하고 집계 보고서와 동결 코드를
  새 비공개 디렉터리에 저장합니다. 덮어쓰기·Git 저장소 내부·raw root 내부 출력을 거부합니다.
- 출력의 고유 관측 수, 반복 평가 수, 제외 시점·이유와 숫자 요약을 연결해 읽어 보세요.
- 실제 입력·결과는 공개 예제와 분리합니다. 공개 시연은 합성 예제만 사용합니다.

연습:

1. 합성 Parquet 테스트에서 파일 한 바이트를 바꿨을 때 replay가 거부되는 이유를 설명하세요.
2. pin 이후 새 파일을 추가해도 결과에 자동 편입되지 않는 것을 테스트에서 확인하세요.
3. 같은 manifest와 동결 코드를 사용해 CSV가 동일하게 재생되는지 비교하세요.
4. 수치 일치만으로 UTC 정확성·시장 대표성·가격 예측력을 증명할 수 없는 이유를 설명하세요.

## 9. observed_outcome — 미래 관측 경로의 라벨

- 입력: 한 판단 시점, 그때 알려진 기준 mid, 고정 horizon·장벽·가격 공백 규칙,
  발생 시각과 수신 시각을 가진 context 목록.
- 출력: 최초 관측 상방/하방/미도달 라벨(+1/-1/0), 미래 mid 변화(bps),
  최초 도달·종료 관측 시각, 또는 null 라벨과 명시적인 검열·모호성 사유.
- `upper/lower = reference * (1 ± barrier_bps / 10000)`이며 경계를 포함합니다.
- 미래 창은 `decision < received <= end`입니다. event도 decision 이후여야 합니다.
  event≤receive, 동일 출처·자산·세션, event 나이·연속 수신 공백도 검사합니다.
- 수신 시각별 가격을 묶어 순서를 알 수 없는 동시 상·하 도달은 모호하게 남깁니다.
- 조기 도달을 발견해도 전체 horizon이 적격해야 합니다. 관측 끝을 넘는 창은
  미도달(0)이 아니라 검열(null)입니다. 끝 가격은 end 이전의 신선한 마지막 관측입니다.
- `(terminal / reference - 1) * 10000`은 가격 변화이며 전략 손익이 아닙니다.
  장벽 비교에는 Decimal을 사용하고 출력은 float입니다.

연습:

1. reference=100, 장벽=10bps일 때 upper=100.1, lower=99.9를 손으로 계산하세요.
2. 가격이 100→100.1→99.8이면 상방 우선인데 종료 변화는 음수가 될 수 있는 이유를 설명하세요.

5. horizon 이후의 가격을 크게 바꿔도 이전 결과가 바뀌지 않는 테스트를 찾아 설명하세요.

## 10. study_events / event_study_io — 고정 특징과 미래 결과 연결

- `study_events(features, contexts, books, policy, rules)`는 Phase 2의 각 판단 시점을 보존하고
  horizon별 결과 행과 LGI 구간별 분모·빈도·제외 이유를 반환합니다.
- OBI는 같은 Phase 2 BBO의 event/receive 시각을 재확인한 경우에만 계산합니다.
  LGI/OBI 공통 코호트 표는 같은 미래 결과 행을 쓰지만 예측 우월성 점수가 아닙니다.
- 특징의 최대 event/receive가 decision을 넘으면 해당 특징을 제외합니다.
  미래 가격은 라벨 계산에만 사용하고 특징·계정 선택을 바꾸지 않습니다.
- 30초마다 5분 결과를 만들면 창이 중첩됩니다. 시작점부터 horizon 간격의 보조 표도
  생성하지만, 시장 국면과 계정 상태가 공유되므로 독립성은 여전히 주장하지 않습니다.
- `register_study`는 결과 계산 전에 규칙·Phase 2 산출물 해시를 등록합니다.
  `run_study`는 고정 입력과 기존 소스를 검사하고 Phase 2 CSV를 동일하게 재생한 뒤
  라벨·정적 HTML·동결 소스를 새 비공개 경로에 저장합니다. 원본 자료는 복사하지 않습니다.
- First Passage의 관측 경로·검열·동시 도달 원칙은 기존 연구를 참고했고,
  출처·as-of 연결·Decimal 경계·공통 코호트·보고서는 이 저장소에 독립 구현했습니다.
  합성 테스트의 일치는 실제 데이터의 예측력을 검증하지 않습니다.

연습:

## 11. research_walkthrough — 합성 반사실적 분해

이 예제는 새 연구 엔진이 아니라 기존 계산 함수를 연결한 작은 공개 시연입니다.
비공개 역사 실험의 데이터·스크립트·통계량을 배포하지 않습니다.

- `synthetic_inputs()`: 기존 합성 시장 경로와 두 계정을 재사용하고 +60초에 한 계정의
  수량을 갱신합니다. 같은 계정의 모든 자산 자식 행도 함께 만들어 완전성을 유지합니다.
- `positions_at(data, policy, decision)`: 당시까지 알려진 합성 계정을 `select_asof`로
  선택해 BTC의 수량·청산가를 반환합니다. 미래 자식 행은 완전성에 사용하지 않습니다.
  이 예제 전용 어댑터이며 일반 실제 자료 로더가 아닙니다.
- `reprice(positions, price, policy)`: 동결한 합성 상태를 `prepare_exposure` → `gravity` →
  `liquidation_imbalance`로 계산합니다. 청산가가 전부 부적격이면 0을 만들지 않고 거부합니다.
- `run_demo()`: 네 미시구조 지표, 역사 특징과 Event Study, +30초→+60초 분해를 반환합니다.
  데모는 stdout만 출력하며 외부 API·개인 자료·파일 쓰기를 사용하지 않습니다.

```text
B = F(P_b,S_b), A = F(P_t,S_t), PO = F(P_t,S_b), SO = F(P_b,S_t)
price_effect = PO-B
state_effect = SO-B
interaction = A-PO-SO+B
A-B = price_effect + state_effect + interaction
```

입력 상태에는 수량·청산가뿐 아니라 관측 계정·결측·신선도도 영향을 줍니다.
이 예제는 두 개의 완전한 인공 계정만 다루며 역사 실험의 상태 분류기를 제공하지 않습니다.
합계가 맞는 것은 항등식 검증이지 인과적 기여도·예측력 증명이 아닙니다.
가격을 먼저 바꾸는 순차 분해와 상태를 먼저 바꾸는 순차 분해는 기여 배분이 달라집니다.

연습:

1. +30초에서는 이전 수량이 선택되고 +60초에서는 새 수량이 선택되는 테스트를 설명하세요.
2. 수량을 바꾸지 않고 가격만 바꾸면 Actual과 Price-Only가 같아지는 이유를 설명하세요.
3. 가격을 바꾸지 않으면 Actual과 State-Only가 같아지는 이유를 설명하세요.
4. 상호작용을 빼고 두 효과를 더했을 때 항등식이 깨지는지 합성 숫자로 확인하세요.
5. 단순 snapshot ID 갱신, signed size 변경, stale 전환을 각각 어떻게 구분해야 할까요?
6. LGI 수준값 상관이 높아도 변화량 재현이나 미래 가격 예측을 증명하지 못하는 이유를 설명하세요.

공개 면접 설명에서는 직접 실행·수정·검증한 범위와 AI 보조를 구분하세요.
