# 대표 사례: 공유 담보·손실 관측·원장 복구

하나의 합성 입력으로 주문 승인·거부, 위험 관측, 수동 청산과 저장 원장을 확인한다.
실행은 저장소 루트에서 `python examples/portfolio_case.py`다.
실행 중 외부 요청은 없으며 임시 SQLite DB는 종료 시 정리한다.

## 입력과 질문

BTC·ETH 두 가상의 선형 상품이 현금1,000을 공유한다. 계약 승수는1이고 수수료는0이다.
수수료가 있는 손계산은 [단일 상품 예제](../examples/execution_walkthrough.py)와
[대응 테스트](../tests/test_execution.py)에 별도로 있다.

호가는 0초에 BTC99/101, ETH9/11이고, 3초에 BTC109/111,
5초에 ETH1/3으로 변한다. 수신 지연 없는 인공 snapshot이고 주문 지연은1초다.
주문·상품·계정 한도는 각각1,000으로 두어 공유 담보와 가격 손실을 중심으로 본다.

질문은 “한 주문을 거부한 뒤에도 다른 주문과 원장이 올바르게 처리되는가”,
“종료 시 청산돼 사라진 중간 위험을 기록하는가”, “재전달·재열기 후에도 같은 원장인가”다.

## 처리 경로와 손계산

| 도착·관측 시각 | 처리 | 계정 또는 판단 근거 |
|---|---|---|
| 1초 | BTC long5를 ask101에 진입 | 원가505, mid 평가손익-5, equity995 |
| 2초 | ETH long50의 진입 초안 | 원가550 추가 시 equity945/예약1,055 → 거부 |
| 4초 | BTC2를 bid109에 청산 | 실현+16, 현금1,016, 남은 BTC 원가303 |
| 4초 | 별도 ETH 신규 주문50을 ask11에 진입 | equity993/예약853/gross830 → 승인 |
| 5초 | ETH mid가2로 하락 | BTC 미실현+27, ETH 미실현-450 → equity593/예약853/여유-260 |
| 6초 | 미리 적은 ETH 청산50을 bid1에 실행 | 실현-500, 현금516, BTC 평가 포함 equity543/필요330 → 위험 해소 |
| 7초 | 미리 적은 BTC 청산3을 bid109에 실행 | 실현+24, 최종 현금540, 보유0 |

```text
BTC 실현 손익 = 2*(109-101) + 3*(109-101) = +40
ETH 실현 손익 = 50*(1-11) = -500
전체 실현 손익 = -460
최종 현금 = 1,000 - 460 = 540
```

거부된 ETH 주문은 수수료·포지션·호가 잔량을 바꾸지 않는다.
4초의 신규 주문은 미리 별도 ID로 적은 입력이며 엔진이 거부 주문을 자동 재시도한 것이 아니다.
5초의 위험은 관측 결과다. 6·7초 청산도 미리 적은 수동 주문이며 자동 강제청산이 아니다.
위험 구간은5초부터6초까지 기록된다. 기록을 위해 체결 결과를 변경하지 않는다.

## 저장·재열기

처음3개 완료 이벤트(BTC 진입, ETH 거부, BTC 부분 청산)를 저장한 뒤 연결을 닫는다.
다시 열어 첫 이벤트를 재전달하면 `duplicate`이며 현금과 포지션을 추가 반영하지 않는다.
이후3개 완료 이벤트를 처리하면 최종 현금540/실현손익-460/보유0으로 연속 실행과 일치한다.
거부 이벤트도 순서에 포함돼 총6개가 저장되며, 체결은5개다.

이는 고정한 전체 입력으로 계산한 완료 이벤트를 저장·재생한 시연이다.
시장 호가 잔량이나 네트워크 미응답 주문의 실시간 복구를 구현한 것은 아니다.
커밋 전후 실제 프로세스 종료는 [저널 테스트](../tests/test_execution_journal.py)에서 별도로 검증한다.
