# 제출본 개선 계획

## 목표와 작업 방식

청산 노출 연구의 시점 정합성과 주문 실행·원장 처리를 작은 합성 예제로 설명한다.
실제 OMS나 검증된 매매 전략으로 표현하지 않는다. 원본 Liquidation_gravity는 읽기만 한다.
단계마다 구현·검증 결과를 보고 다음 범위를 수정한다. 아래 후보는 확정 기능 목록이 아니다.

**현재 상태: v1 후보의 구현·대표 사례·문서를 고정했다. 공개 여부는 Git 커밋과 원격 상태로 확인한다.**
실제 거래소 기능·Linux 운영 검증·개인의 학습 완료는 이 완료 범위에 포함하지 않는다.
사용자의 요청에 따라 마감 여부는 작업 판단에서 제외한다.

## 3단계 결과 — 공유 담보와 위험 판단 근거

- 실행 엔진은 상품별 호가·포지션과 공통 현금을 관리한다. 상품별 보유 포지션은 하나다.
- `execution_risk.py`에 현재 계정 평가와 진입 후 예상 수치 계산을 분리했다.
- 주문에 `risk.before/candidate/projected/after/status/reason`을 기록한다.
  equity, 예약 담보, gross 노출, 필요 담보, 담보 여유와 가격 근거를 확인할 수 있다.
- 모든 상품은 같은 담보/손익 통화와 승수1의 합성 선형 계약이다. cross-currency나
  거래소 간 담보 이전은 구현하지 않는다. long/short 노출은 상계하지 않는다.

## 5단계 — 합성 주문 이벤트 저장과 원장 복구

설계 판단과 범위 조정:

- 기존 엔진의 fill 원장 계산을 `execution_ledger.rebuild_account`로 분리했다.
  원래 최종 검산과 저장 후 재생이 이를 공유하고, 기존 손계산 테스트를 유지했다.
- 새 `ExecutionJournal`은 고정한 합성 입력의 처리 완료 주문 이벤트를 저장한다.
  한 IOC 주문에 하나의 완료 이벤트와 선택적인 집계 체결이 대응한다.
- 실시간 엔진의 시장 상태 체크포인트 대신 전체 원장 재생을 선택했다.
  입력 전체와 예상 이벤트가 이미 정해진 오프라인 시연이며 실제 exchange ingest가 아니다.
- 이벤트와 반영 후 원장을 SQLite 단일 트랜잭션으로 저장한다.
  같은 ID·같은 내용은 중복 처리, 내용 상충·순서 누락은 오류로 남긴다.
- 입력/코드 해시와 이벤트 prefix/원장을 재열기 때 검증한다. 원장 불일치를 자동 복구로 덮어쓰지 않는다.
  해시는 로컬 재현 근거이며 외부 진위 인증은 아니다.
- 호가 잔량·대기 주문·미응답 주문·실시간 재연결 대사는 이번 복구 범위에 포함하지 않는다.

## 9단계 검토 — 보유 중 위험 상태 관측 (2026-11-04)

사용자가 다음 방향으로 추가 개발의 필요 기능 검토를 선택했다.

이번 검토에서 금융 코드를 변경하지 않았다.

확인한 빈틈은 보유 중 위험 상태의 기록이다. 기존 계약은 주문 전후/종료 시점만 평가하므로
중간에 발생했다가 회복된 담보 부족과 stale 구간은 결과만으로 확인하기 어렵다.
현재 동작은 문서화한 범위에 맞지만, 포지션·리스크 모듈을 발전시키려면 보완할 가치가 있다.

재현 근거:

- 초기 담보204, 수수료0, long2를 ask101에 진입하면 mid100에서 equity202/예약202로 승인된다.
  t3에서 mid50이면 equity102/예약202, 담보 여유-100이다. t4에 mid100으로 회복시키면
  종료 여유0만 남고 중간 위험 이벤트 출력은 없다. 다음 주문도 없으므로 신규 진입 검사로 드러나지 않는다.
- 최대 quote age1초에서 t1에 진입하고 t4에 새 호가를 받으면, t1+1ns부터의 가격 평가 공백이
  있어도 종료 시각 t5의 가격은 신선하다. 현재 결과에 공백 구간 기록은 없다.

권장하는 다음 구현은 **합성 리플레이의 보유 중 위험 관측**이다.

1. 관측 상태를 정상·담보 한도 위반·가격 평가 불가로 구분한다.
2. 호가 반영, 체결 반영, 현재 호가의 만료, 종료 시점에서 계정 수치를 기록한다.
   같은 시각에는 현재 엔진의 호가/청산/진입 순서를 유지하고, 새 호가로 대체된 옛 만료는 무시한다.
3. 위험 상태가 시작·변경·해소되는 시각과 원인, equity·예약·gross·headroom 및 가격 근거를 남긴다.
4. 감시 결과가 주문 승인·체결·현금·포지션을 바꾸지 않도록 기존 결과와 대조한다.
5. 미래 가격이 이전 관측을 바꾸지 않는지, 오래된 호가가 새 상태를 덮지 않는지 확인한다.

완료 기준은 위 두 재현 구간의 검출, 정상 복귀 구분, 정확한 만료 경계, 가격 부재를0으로
표현하지 않는 것과 기존 체결·원장의 불변성이다. 자동 강제청산·경보 전송·실시간 서비스는 포함하지 않는다.
저널은 여전히 현금·포지션 복구만 담당한다. 이 검토는 아직 위험 모니터링 구현 완료를 뜻하지 않는다.

우선순위는 이 기능이 가장 높다. 주문별/상품별 추가 한도 설정은 그 다음 검토 대상이며,

  설정 한도 위반은 주문·상품(symbol순)·계정 순서로 대표 사유를 정한다.
- 수량 감소 청산은 진입 한도에서 제외하되 기존 호가·session·보유 수량 검사를 유지한다.
  다른 보유 상품의 한도 초과도 신규 진입을 막는다. 거부 시 비용·깊이·원장을 변경하지 않는다.
- 모니터는 exposure_limit_breach와 위반 항목 변경·회복을 기록한다.
  가격 부재가 있으면 최우선으로 평가 불가를 표시하며, 알려진 상품 위반은 보존한다.
  모르는 검사 값·여유·passed는 null이다. 자동 주문이나 강제청산은 수행하지 않는다.
- 한도 정책은 동결 입력 해시에 포함된다. 한도로 거부된 주문의 저장/복구도 검증했다.
  코드 버전 변경 시 기존 저널을 자동 이관하지 않는 기존 원칙을 유지한다.

검증 결과:

- 한도 전용 테스트24개 추가, 전체 **405 passed, skip0**.
  Python3.13.15 및 깨끗한 비편집 설치의 Python3.11.6에서 전체 검증을 통과했다.
- 데모11개·로컬 문서 링크·pip check 정상. 새 risk_limits.py는 세 한도의 거부와 보유 중 회복을 출력한다.
- 정확한 경계/1 quantum 초과, 부분 체결 요청, 깊은 체결 가격, 거부 시 잔량 보존,
  공유 담보와 별도 계정 한도, 청산 예외, 다른 상품의 기존 위반, 미평가 상태와 위반 공존,
  여러 한도의 일부 회복, 잘못된 설정과 기존 기본 동작을 검증했다.
- policy=None의 오류 형태가 TypeError가 되는 회귀를 실패 테스트로 재현하고,
  타입 검증을 선행해 ValueError로 거부하도록 수정했다.

현재 추가 범위는 설정형 위험 정책과 합성 관측까지다. 실제 거래소·운영 한도나 규제 기준은
등록하지 않았으며 값을 실제 사양으로 해석하지 않는다. 원본 수정·커밋·업로드는 수행하지 않았다.

## v1 공개 정리

위 단계별 기록은 당시의 작업 이력이다. v1에서는 새 금융 기능을 추가하지 않고,
처음 읽는 사람이 확인할 대표 사례와 공개 문서 구조를 정리했다.

- README는 목적·실행·대표 결과·설계 근거·범위 중심으로 줄였다.
- 상세 계약과 학습 자료는 docs/, 이 계획과 초기 공개 감사는 docs/development/에 보관했다.
- 회사별 지원 메모는 Git 제외 대상 local/SUBMISSION.md로 옮겼다. 공개 배포 파일에 포함하지 않는다.
- portfolio_case.py는 같은 합성 입력에서 주문 거부·담보 해제·중간 위험·수동 청산·저널 복구를 연결한다.
  BTC 실현+40/ETH 실현-500/수수료0 → 최종 현금540을 손계산과 대조한다.
  위험 시작5초(headroom-260)와 청산 후 해소6초를 기록한다. 미리 정한 주문이며 자동 강제청산이 아니다.
- 사례 통합 테스트2개를 추가해 전체407개·데모12개를 검증한다.
- 전체 검증 스크립트는 공개 docs/의 로컬 링크도 검사한다. 개인 지원 메모와 외부 URL/anchor는 제외한다.
- MANIFEST는 공개 문서를 docs/에서 포함하고 local/을 제외한다.

원본 Liquidation_gravity는 수정하지 않았다. GitHub 게시 전 변경 파일·배포 포함과 전체 검증을 확인한다.
이후 기능 확대보다 사용자가 설계 판단과 한계를 설명할 수 있는지 점검하는 것이 우선이다.
